# New API 功能补齐任务规划书

## 背景

基于《New API 项目功能调研报告》，现有系统存在部分功能缺口。本文档对"不支持"或"间接支持"的功能进行统一规划，明确实现路径、优先级与验收标准。

---

## 功能缺口总览

| 模块 | 缺口功能 | 当前状态 | 目标状态 |
|------|----------|----------|----------|
| Chat 聊天 | 文生图测试 UI | 后端支持，前端无界面 | 前端新增文生图体验页面 |
| Chat 聊天 | 文生视频测试 UI | 后端支持，前端无界面 | 前端新增文生视频体验页面 |
| Chat 聊天 | TTS 测试 UI | 后端支持，前端无界面 | 前端新增 TTS 体验页面 |
| 登录认证 | 手机号登录 | 完全不支持 | 支持手机号+短信验证码注册/登录 |
| 安全防护 | 全局入站 IP 黑名单 | 完全不支持 | 支持全局 IP/CIDR 黑名单拦截 |
| 运维监控 | 内置主动探测 | 依赖外部 Uptime Kuma | 支持内置渠道健康探测与状态展示 |

## 任务一：文生图体验页面

### 目标
在 Playground/体验中心增加专门的文生图测试界面，用户可选择自己的 API Key 并直接调用后端 `images/generations` 接口。

### 实现要点
1. **前端页面**
   - 新增路由 `/playground/images` 或 `/experience/images`
   - 输入表单：prompt、model（下拉选择）、size、quality、n、style
   - API Key 下拉选择器（过滤有额度的 key）
   - 结果展示区：图片网格 + 下载按钮
   - 支持流式/非流式响应适配

2. **后端**
   - 复用现有 `relay` 的 `images/generations` 端点，无需改动
   - 如需体验中心独立部署，确保 CORS 和认证透传正常

3. **安全**
   - API Key 调用走正常计费链路
   - 前端不暴露 key 的完整内容，仅显示名称后几位

### 验收标准
- [ ] 页面可正常打开，未登录用户提示登录
- [ ] 支持主流文生图模型（DALL-E 系列、Stable Diffusion 等）
- [ ] 生成结果可预览和下载
- [ ] 计费记录正确写入

### 预估工时
- 前端：3 人日
- 后端：0.5 人日（联调）

## 任务二：文生视频体验页面

### 目标
在 Playground/体验中心增加专门的文生视频测试界面，调用后端 video 相关 task 端点（sora、kling、vidu 等）。

### 实现要点
1. **前端页面**
   - 新增路由 `/playground/videos` 或 `/experience/videos`
   - 输入表单：prompt、model（下拉选择）、duration、resolution、aspect_ratio 等
   - API Key 下拉选择器
   - 结果展示区：视频播放器 + 下载按钮
   - 由于视频生成通常异步，需增加"任务状态"轮询或 WebSocket 通知

2. **后端**
   - 复用现有 video task 端点
   - 如需新增统一的任务状态查询接口，评估是否必要

3. **异步任务处理**
   - 前端轮询任务状态（polling）
   - 生成完成后展示结果

### 验收标准
- [ ] 支持主流文生视频模型
- [ ] 任务提交后可查看状态（排队中/生成中/完成/失败）
- [ ] 生成结果可播放和下载
- [ ] 失败时展示错误原因

### 预估工时
- 前端：4 人日
- 后端：1 人日（任务状态接口）

## 任务四：手机号登录

### 目标
支持用户通过手机号 + 短信验证码完成注册和登录。

### 实现要点

#### 4.1 短信服务商接入
- 评估并选择短信服务商（阿里云 SMS、腾讯云 SMS、Twilio 等）
- 配置短信模板（验证码模板）
- 实现统一的 SMS Provider 接口，方便后续切换

#### 4.2 后端接口
1. **发送验证码接口**
   - `POST /api/sms/send`
   - 参数：phone（手机号）、type（register/login/reset）
   - 限流：同一手机号 60 秒内只能发送一次，同一 IP 每天最多 10 次
   - 验证码存储：Redis，TTL 5 分钟

2. **手机号注册接口**
   - `POST /api/user/register/phone`
   - 参数：phone、code（验证码）、password（可选）
   - 流程：验证验证码 -> 检查手机号是否已注册 -> 创建用户 -> 生成 JWT

3. **手机号登录接口**
   - `POST /api/user/login/phone`
   - 参数：phone、code
   - 流程：验证验证码 -> 查找用户 -> 生成 JWT
   - 支持"验证码快捷登录"（无需密码）

4. **用户表扩展**
   - `users` 表增加 `phone` 字段，VARCHAR(20)，唯一索引
   - 迁移脚本需兼容 SQLite/MySQL/PostgreSQL

5. **绑定/换绑手机号**
   - 已登录用户可在设置中绑定或更换手机号
   - 换绑需验证旧手机号或当前登录状态

#### 4.3 前端页面
- 登录页增加"手机号登录" Tab
- 注册页增加"手机号注册"选项
- 个人设置页增加"手机号绑定"入口
- 输入框：手机号（带区号选择，默认 +86）、验证码（6位数字）
- 倒计时重新获取验证码

#### 4.4 配置项
- 后台新增 SMS 配置：
  - `SmsEnabled`：是否启用短信功能
  - `SmsProvider`：服务商类型
  - `SmsAccessKeyId` / `SmsAccessKeySecret`：密钥
  - `SmsSignName`：短信签名
  - `SmsTemplateCode`：验证码模板代码

### 验收标准
- [ ] 可正常发送短信验证码（限流有效）
- [ ] 支持手机号注册新账号
- [ ] 支持手机号+验证码登录
- [ ] 支持已登录用户绑定/换绑手机号
- [ ] 验证码过期或错误时给出明确提示
- [ ] 同一手机号不能重复注册
- [ ] 与现有 OAuth 登录方式并存，不冲突

### 预估工时
- 后端：5 人日
- 前端：3 人日
- 测试：2 人日

## 任务五：全局入站 IP 黑名单

### 目标
在 middleware 层增加全局 IP 黑名单拦截，命中黑名单的所有入站请求直接返回 403。

### 实现要点

#### 5.1 配置设计
- 后台新增配置项：
  - `GlobalIPBlacklistEnabled`：是否启用全局黑名单
  - `GlobalIPBlacklist`：黑名单列表，支持 IP 和 CIDR（如 `192.168.1.1`、`10.0.0.0/8`）
  - 存储格式：JSON 数组字符串

#### 5.2 Middleware 实现
1. **新增中间件 `GlobalIPBlacklistMiddleware`**
   - 注册在所有路由之前（或紧随 GlobalWebRateLimit 之后）
   - 提取请求真实 IP（需考虑 X-Forwarded-For、X-Real-IP）
   - 遍历黑名单列表，IP 匹配或 CIDR 包含时返回 403
   - 命中时记录日志（可选）

2. **IP 解析工具**
   - 复用现有 `middleware/ip.go` 中的 IP 提取逻辑
   - 新增 CIDR 匹配函数（Go 标准库 `net` 包即可实现）

3. **性能考虑**
   - 黑名单列表在应用启动时加载到内存
   - 配置变更时热重载（或走现有配置刷新机制）
   - 黑名单规模较大时，考虑用 Radix Tree 优化匹配性能（初期列表短，无需过度设计）

#### 5.3 管理界面
- 后台系统设置页增加"全局 IP 黑名单"配置面板
- 支持批量输入（每行一个 IP/CIDR）
- 展示当前命中统计（可选增强）

### 验收标准
- [ ] 黑名单中的 IP 访问任何接口均返回 403
- [ ] CIDR 格式黑名单可正确拦截网段
- [ ] 不在黑名单中的 IP 访问不受影响
- [ ] 配置变更后无需重启即可生效
- [ ] 支持 IPv4 和 IPv6（如适用）

### 预估工时
- 后端：2 人日
- 前端：1 人日
- 测试：1 人日

## 任务六：内置渠道主动探测

### 目标
减少对外部 Uptime Kuma 的依赖，在系统内部实现渠道健康状态主动探测，并在首页/后台展示状态面板。

### 实现要点

#### 6.1 探测机制
1. **探测任务调度**
   - 使用 Go 的 `time.Ticker` 或定时任务库（如 cron）
   - 可配置探测间隔（默认 5 分钟）
   - 后台配置：`ChannelHealthCheckEnabled`、`ChannelHealthCheckInterval`

2. **探测方式**
   - 对每个启用的 Channel，发送一个轻量级测试请求（如小模型 chat completion）
   - 或使用已有的 `ChannelTest` 逻辑
   - 记录响应时间、HTTP 状态码、是否成功

3. **状态存储**
   - 内存缓存：最近 N 次探测结果（用于前端展示）
   - 持久化（可选）：将历史状态写入数据库，用于趋势分析

4. **失败处理**
   - 连续 N 次失败自动禁用 Channel（与现有自动测试逻辑对齐）
   - 恢复后自动启用
   - 发送通知（Webhook、飞书等，可选）

#### 6.2 状态展示
1. **首页状态面板**
   - 复用现有的 Uptime Kuma 面板位置，或新增独立面板
   - 展示各 Channel 的实时状态（在线/离线/未知）
   - 展示最近响应时间

2. **后台渠道列表**
   - 列表页增加"健康状态"列
   - 支持按状态筛选

3. **状态详情**
   - 点击 Channel 可查看最近探测记录和失败原因

#### 6.3 对外接口
- 保留现有 `/api/status` 或新增 `/api/health/channels` 接口
- 返回 JSON 格式的渠道健康状态（无需认证或仅管理员可访问）

### 验收标准
- [ ] 可按配置间隔自动探测所有启用渠道
- [ ] 首页/后台可查看渠道实时健康状态
- [ ] 连续失败自动禁用、恢复自动启用
- [ ] 探测不占用过多系统资源（异步、超时控制）
- [ ] 与现有 Uptime Kuma 集成不冲突（可共存）

### 预估工时
- 后端：4 人日
- 前端：2 人日
- 测试：2 人日

## 技术风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| 短信服务商接口不稳定 | 手机号登录功能不可用 | 抽象 SMS Provider 接口，预留多服务商切换能力 |
| 文生视频异步任务超时 | 用户体验差 | 前端增加清晰的任务状态提示，支持后台继续生成 |
| IP 黑名单误拦截 | 正常用户无法访问 | 默认关闭，配置时提供测试模式；日志记录便于排查 |
| 渠道探测频率过高 | 增加上游成本和系统负载 | 可配置间隔，单渠道探测增加超时控制 |
| 前端页面风格不统一 | 体验割裂 | 统一使用现有 Semi Design 组件库，参考现有 Playground 设计 |
